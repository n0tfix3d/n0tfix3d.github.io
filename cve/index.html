CVE-2026-52778 — Unsafe eval() in Formula Calculator:
Remote Code Execution & Denial of Service

Executive Summary

An unsafe execution vulnerability exists in the Bazar form field calculator (CalcField.php) of YesWiki. The application sanitizes user-defined formulas using a complex recursive regular expression before passing them to PHP's eval(). This is inherently flawed: it is vulnerable to ReDoS / Stack Overflow (guaranteed server crash), and any regex bypass leads directly to arbitrary PHP code execution.

Impact

  • Confidentiality: HIGH — Read sensitive files (/etc/passwd, .env).
  • Integrity: HIGH — Modify application files, inject backdoors, alter database content.
  • Availability: HIGH — Crash the web service immediately via ReDoS / Segmentation Fault.

Technical Analysis

Filetools/bazar/fields/CalcField.php
MethodformatValuesBeforeSave($entry)
Root CauseRecursive regex guard on eval() — exhausts PCRE stack on deep nesting, and any bypass results in arbitrary PHP execution.
$regexp = '/^((' . $number . '|' . $functions . '\s*\((?1)+\)|\((?1)+\))(?:' . $operators . '(?1))?)+$/';

if (preg_match($regexp, $formula)) {
    $formula = preg_replace('!pi|π!', 'pi()', $formula);
    try {
        eval("\$value = $formula;");  // VULNERABLE
  • PCRE Stack Overflow / ReDoS — Pattern (?1)+ recurses on the system stack. Thousands of nested parentheses trigger either recursion limit exhaust or a Segmentation Fault, crashing PHP-FPM.
  • Complete trust in eval() — Complex regex sanitizers for eval() are consistently bypassed historically via edge-case syntaxes, encoding tricks, or PCRE version bugs.

Proof of Concept

A
Remote Denial of Service — Server Crash via ReDoS

Inject a deeply nested formula into a Bazar Calc field (multiply to 2000–5000 iterations based on the server's pcre.recursion_limit):

((((((((((((((((((((((((((((((((((((((((((1+1))))))))))))))))))))))))))))))))))))))))))))

The PCRE engine runs out of stack memory → immediate crash of the PHP-FPM worker → service unavailable.

B
Logical Bypass to RCE — Arbitrary PHP Execution

If the regex is bypassed (via PCRE version-specific bugs or fuzzing), the payload executes as native PHP:

abs(1) + system('id')

Grants attacker www-data privileges → full host compromise.

Remediation

  • Replace eval() with a dedicated, sandboxed AST math parser (e.g., symfony/expression-language or mossadal/math-parser) that cannot invoke system calls.
  • As an interim measure, disable the CalcField component until the eval() path is fully replaced.

CVE-2026-46656 — Improper Authorization leading to Persistent Ghost Sessions

Executive Summary

Bludit CMS is vulnerable to a critical Broken Access Control flaw where active sessions remain valid even after the corresponding user account has been physically deleted from the database. This "Ghost Session" allows revoked users to maintain full unauthorized access — including creating new administrator accounts.

Impact

  • Deleted users retain full session access — Ghost Sessions persist indefinitely after account removal.
  • A revoked admin can create new administrator accounts, regaining permanent access and bypassing all revocation.
  • Actions logged to non-existent entities — audit trail breaks completely.

Technical Analysis

Locationbl-kernel/users.class.php → isLogged()
CVSS VectorAV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H
Root CauseThe kernel trusts $_SESSION and never re-validates user existence in the database on subsequent requests.

Proof of Concept

Scenario: "The Immortal Administrator" — Backdoor Creation via Ghost Session.
1
Administrator creates admin2 (Admin) and author (Author).
2
Main administrator deletes both accounts using "Delete user and content".
3
Database Audit — entries completely removed from the JSON database.
4
Persistence Test — deleted admin2 still using their Ghost Session successfully publishes a new article.
5
Privilege Escalation — deleted admin2 accesses the "Add New User" form.
6
Full Compromise — creates backdoor admin account created_from_deleted_admin2.

Remediation

  • Implement server-side session invalidation that cross-checks user existence in the database on each request.
  • Update disableUser() in bl-kernel/users.class.php to clear tokenAuth and tokenRemember upon account deletion.

CVE-2026-46657 — Persistent Authentication Tokens Not Revoked upon Account Disablement

CVE ID

Executive Summary

When an administrator disables a user account, Bludit fails to invalidate the tokenAuth and tokenRemember fields. Any user with a pre-existing "Remember Me" cookie can bypass account disablement and maintain a valid authenticated state indefinitely.

Impact

  • Disabled accounts remain accessible via persistent "Remember Me" cookies.
  • Standard password login is blocked (password prefixed with !), but the token auth path is completely bypassed.
  • Revoked users maintain unauthorized access indefinitely until tokens are manually cleared.

Technical Analysis

Locationbl-kernel/users.class.php → disableUser()
CVSS VectorAV:N/AC:L/PR:L/UI:N/S:U/C:H/I:L/A:N
Root CausedisableUser() correctly prefixes the password with ! but leaves tokenAuth and tokenRemember intact in bl-content/databases/users.php. The "Remember Me" subsystem validates tokens directly against the DB without checking the disabled flag.

Proof of Concept

1
Create admin2 and author, both logged in with "Remember Me".
2
Main administrator disables both accounts. System confirms disabled.
3
Database check — password invalidated (!) but tokens tokenAuth + tokenRemember unchanged.
4
The disabled author successfully publishes a new post via the persistent token.

Remediation

  • Update disableUser() in bl-kernel/users.class.php to explicitly clear tokenAuth and tokenRemember in the JSON database when disabling an account.

CVE-2026-48488 — Weak Cryptography: SHA-1 Used for Attachment Password Hashing

Executive Summary

Attachment passwords in phpMyFAQ are hashed using SHA-1, a cryptographically broken algorithm since the SHAttered collision attack (2017). The affected component is phpmyfaq/src/phpMyFAQ/Attachment/AbstractAttachment.php.

Impact

  • An attacker can generate SHA-1 collisions to bypass attachment protection.
  • Risk of password cracking if the database is compromised — estimated under 1 minute with modern hardware.

Technical Analysis

CWECWE-328 (Use of Weak Hash)
Locationphpmyfaq/src/phpMyFAQ/Attachment/AbstractAttachment.php

Remediation

Replace SHA-1 with PHP's native password_hash() / password_verify() (bcrypt):

public function setPassword(string $password): void
{
    $this->passwordHash = password_hash($password, PASSWORD_BCRYPT);
}

public function verifyPassword(string $plainPassword): bool
{
    return password_verify($plainPassword, $this->passwordHash);
}
